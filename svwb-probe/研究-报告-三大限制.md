# 研究-报告：HybridCLR 内存读取三项限制的可执行解法

> 目标：《影之诗》国服「影之幻境」（Unity + HybridCLR 热更新，Windows IL2CPP）
> 只读内存工具。**不写内存、不注入、不 hook**。
>
> 本报告所有偏移都经过两类验证之一：
> 1. 用热更新程序集的 ECMA-335 元数据**算出**，再与真机读数逐字段对照；
> 2. 在真机（pid 26920，2026-10-17 19:4x）上直接读出，且用**卡表命中 + 星级匹配**校验。
>
> 产物都在 `svwb-probe\` 下，前缀 `研究-`。

## 0. 结论先行（先看这 10 行）

1. **限制 1、2 其实可以绕过**：`sv2Warchess.bytes` 的元数据足以**精确算出**字段布局。
   旧工具的三个 bug（静态字段当成实例字段、基类字段被忽略、枚举/结构体当成 8 字节指针）
   修掉后，`BattlePlayerBase` 的 8 个字段（含 `ShopCardList@0x50`、`BattleCards@0x60`）
   全部与真机一致。**布局是确定性的，不需要"从已知值反解"**。
   → `研究-exact_layout.py`（27,188 个类型，12 个热更新程序集）

2. 真需要反解时（外部结构体尺寸未知、元数据被混淆），用**约束求解 + 唯一性证书**，
   而不是"DFS 随便挑一组"：重复值场景下，算法会**明确报告歧义**并告诉你
   "再需要 1 个 life≠grade 的实例"。→ `研究-layout_csp.py`（4 个合成场景全部通过）

3. **限制 3 已现场解决**：对方场上随从在
   `WorldData(+0x128).CacheBattleResult → S_COMBAT_OPPONENT(+0x40).minions
   → Il2CppArray<CARD_MINIONS> → CARD_MINIONS(+0x1C).card_id`
   **实测 7/7 卡 ID 命中卡表、7/7 星级匹配**，且 DTO 的 uid/hero/life/grade
   与 `WorldData+0x198` 的对方 `BattlePlayerBase` 完全一致。

4. 旧工具"列表解析是垃圾"的两个根因（都已定位）：
   * **`CARD_MINIONS` 继承 `Netease.GameNet.ProtoBase`（8 字节）**，旧代码忽略基类
     → 所有 `MOS_PROTO` 字段整体**偏移 +8**；`minions` 实际在 `+0x40`，旧代码读 `+0x38`
     （那是 `grade + random_num` 拼成的假指针）。
   * `minions` 是 **`Il2CppArray<T>`（数组）**，不是 `List<T>`；旧代码按 List 读
     `_items@+0x10 / _size@+0x18` → 实际读到 `bounds=0` 和数组长度。

5. "扫 `BattleCardBase` 得到 800000xx、卡表命中 0%" 是**伪失败**：
   800000xx 是**堆指针的低 32 位**（例如 `0x7FF804C4B3F2` 的低半字 = 80,000,000 附近），
   旧代码"取第一个 8 位数"必然先撞上指针。真实卡 ID 在 `[[card+0x10]+0x10]`
   （`_buildInfo.CardId`），实测 330~336 个实例里 **103~112 个**能读出合法卡 ID。

6. **不要用 `isEnemy`/`isFiled` 区分敌我**：真机上 65 个 `LocationType=2`（场地）的
   `BattleCardBase`，`OwnerType` 全是 0、`isFiled` 全是 0、`isEnemy` 全是 0。
   这些字段名有误导性，不能作为判据。

7. 对方随从**不是** `BattleCardBase` 列表：整个程序集里没有任何"对方场"的
   `List<BattleCardBase>` 字段。对方场只在**服务端 DTO** 和 **UI 视图**里。

8. 系统化搜索算法（不依赖具体类）：**卡 ID 值扫描 → 记录模板反推 → 容器/owner 反推**。
   本机实测：5,336 个卡 ID 命中 / 20.8 秒；3,725 条记录；9,092 个反向指针；71 个数组；
   总 61.3 秒（当前进程私有内存）。按 5.4GB 线性外推约 2 分钟，仍远低于"10 分钟"。
   命中排行里 `S_COMBAT_OPPONENT+0x40/+0x50` 被元数据 join 自动认领。
   → `研究-find_opponent.py`

9. 验证判据只有三样可信：**(a) 卡 ID ∈ 卡表 174 个 ID**、**(b) `star` 与卡表一致**、
   **(c) owner 字段在元数据里确实声明为 `CARD_MINIONS[]`**。三者同时满足才认。

10. **明确的"不行"**：如果某天服务端不再把对方卡 ID 下发给客户端（战争迷雾），
    那任何只读内存都拿不到——但**本版本不是这样**，卡 ID 就在 DTO 数组里。

## 2. 限制 1：已知值重复时无法区分

### 2.1 先说结论

**不要从值反解布局**——先把布局算出来。元数据够，就没有"重复值"问题。

旧 `hybridclr_layout.py` 的 `brute_force()` 只在"元数据不可信"时才有意义。
而在那种情况下，单实例、重复值、无额外约束时，**数学上不可能唯一**：

> **命题（重复值不可分辨）**：设两个字段 `f1, f2` 宽度相同、值域相同，在同一个实例里
> 已知值都是 `v`，候选偏移集合都是 `{p, q}`，且所有约束只涉及"偏移、宽度、值"。
> 那么交换 `(f1→p, f2→q)` 与 `(f1→q, f2→p)` 是约束系统的**自同构**，
> 至少存在 2 组解。**仅凭这一个实例，任何算法都无法区分。**

所以正确做法不是"更聪明的 DFS"，而是：
1. 补上**不依赖人工真值**的结构约束（引用 oracle、枚举值域、`instance_size`、声明顺序）；
2. 用**多实例交叉**产生见证；
3. 用**事件差分**自动产生新真值；
4. 最后用**逐字段可行性检验**给出"唯一性证书"，而不是"挑一组"。

### 2.2 布局确定性优先：`研究-exact_layout.py`

旧工具的三个致命 bug（都在 `load_classes()` / `type_size()` / `layout_*()` 里）：

| bug | 后果 |
|-----|------|
| `F static int X` 被正则当成字段（type="static"、name="int"） | `_types_warchess.txt` 里 **3,175 / 11,660 行（27.2%）是 static**，WorldData/BattleView 等布局全被污染 |
| 基类字段被忽略 | `ProtoBase` 的 8 字节没算 → 所有 `MOS_PROTO` 偏移 -8 |
| 枚举/结构体一律当 8 字节引用 | `CardLocationType`（4 字节枚举）、`Vector3`（12 字节）、`BuffStateFlag`（2 字节）全部算错 |

正确规则（x64 IL2CPP，HybridCLR 解释器类与 AOT 类一致）：

```
对象头 0x10（klass + monitor）
基类字段在前（从 System.Object 往下逐层）
本类字段：声明顺序 + 自然对齐（align = min(size, 8), pack = 8）
static / literal 字段不占实例空间
枚举尺寸 = value__ 的底层类型
值类型内联；引用类型一律 8
外部结构体（UnityEngine.Vector3 等）按已知表内联
```

`研究-exact_layout.py` 已实现并验证。它可以对 12 个热更新程序集的
**27,188 个类型**算布局，命令：

```bat
python 研究-exact_layout.py layout Sv2Warchess.Sv2WarchessBattlePlayerBase
python 研究-exact_layout.py layout Netease.GameNet.MOS_PROTO.CARD_MINIONS
python 研究-exact_layout.py verify
```

### 2.3 反解时的约束模型（`研究-layout_csp.py`）

变量：每个字段的偏移 `o_f ∈ [0x10, end-size_f]`。约束：

**硬约束（不依赖真值）**

| 编号 | 约束 | 作用 |
|------|------|------|
| H1 | 区间不重叠 + 自然对齐 | 排除 90% 的乱组合 |
| H2 | 声明顺序单调（顺序布局） | 重复值 `life=grade=6` 在 `0x1c/0x24` 时被顺序定死 |
| H3 | `max(o_f+size_f) ≤ instance_size` | 从 Il2CppClass 读，砍掉越界候选 |
| H4 | 宽度精确匹配 | int16 字段不能拿 int32 的 6 去命中 |
| H5 | **引用 oracle**：引用字段必须指向 null 或**期望类型的对象** | 不需要任何真值，钉死所有引用字段 |
| H6 | 枚举/布尔/整型值域 | `Grade∈1..12`、`OwnerType∈{0,1,2}`、`bool∈{0,1}` |

**自动约束（也不需要人工真值）**

| 编号 | 约束 | 实现 |
|------|------|------|
| A1 | 多实例交叉：同一字段在所有实例上必须同时满足各自已知值 | `occurrences()` 交集；`life=6/12, grade=6/3` 两实例即可分开 |
| A2 | 列统计先验：候选偏移在其它实例上读出指针/越界值 → 否决 | `column_ok()` |
| A3 | 结构不变式：`MaxLife≥Life`、`Armor≥0`、`HandCardNum==HandCards.Count`、uid 唯一 | 可插拔 `invariants` |
| A4 | **事件差分 oracle**：已知事件前后 diff | 见 §3.3，最便宜的新真值来源 |

### 2.4 唯一性证书（不是"跑一遍 DFS 就完事"）

```
算法 unique(field f):
    feas = []
    for o in candidates[f]:
        if SAT(assign f=o):        # 带全部约束回溯，找到一个解即停
            feas.append(o)
    if len(feas)==1:  f 唯一 = feas[0]
    else:              f 仍歧义，报告 feas
```

* 如果所有字段都 `len(feas)==1` → **有证明的唯一解**（相对于约束模型）。
* 只要有一个字段 `len(feas)>1` → **明确报告歧义**，绝不"随便挑"。
* 还能给出**需要什么额外观测**：

```
建议: 需要 1 个 Life != Grade 的实例（同一实例里两者值不同）：
      目前二者都可落在 ['0x24', '0x34']
```

这就是对限制 1 的直接回答：**不是猜，而是把"缺哪个见证"算出来给用户**。

### 2.5 自测输出（`python 研究-layout_csp.py selftest`）

## 3. 限制 2：已知值太少时不唯一

### 3.1 最少需要几个？分情况给答案

| 前提 | 最少已知值 | 说明 |
|------|-----------|------|
| 元数据完整（基类/值类型/静态/外部结构体都正确） | **0** | 布局是算出来的；已知值只用于**校验**，不参与求解 |
| 顺序布局 + 所有尺寸已知 + 有 `instance_size`/引用 oracle | **0~1** | 一个唯一值可锚定其所在连续块；引用字段由 H5 钉死 |
| 顺序布局 + 某个外部类型尺寸未知 | 每个"尺寸歧义"至少 1 个能区分的值 | 枚举外部类型尺寸 `{4,8,12,16,...}`，用已知值筛选 |
| 完全乱序（无顺序模型） | 每个字段至少 1 个"区分性"观测 | k 个已知值最多钉死 k 个字段；重复值还需见证实例 |
| 只有 1 个实例 + 重复值 + 无任何结构约束 | **不可能**（§2.1 命题） | 需要第 2 个实例或一个 oracle |

### 3.2 自动产生约束/真值的 6 种办法（按性价比排序）

1. **元数据精确布局（首选，0 成本）**
   直接算，不需要真值。`研究-exact_layout.py`。

2. **引用 oracle（0 人工真值，立即可用）**
   字段类型是 `List<X>` / `X[]` / `Dictionary<K,V>` 时，偏移处必须指向
   `null` 或 klass 名匹配的对象。`BattlePlayerBase` 有 7 个列表字段，
   这一条就把 7 个偏移全部钉死。自测场景 4：0 个已知值、两个引用字段唯一。

3. **枚举/布尔值域（0 人工真值）**
   `CardLocationType∈{0,1,2}`、`CardOwnerType∈{0,1,2}`、`BuffStateFlag` 是
   位标志（`short`）、`bool∈{0,1}`。候选偏移里凡是读出 32760、-1344472880
   这类值的，直接否决。

4. **跨实例列一致性（0 人工真值，但需要同类多实例）**
   扫描同类全部实例，对每个候选偏移统计：是否恒为指针（int 字段不可能）、
   是否越界、是否恒定。真字段的列像"人类数据"，假字段像"内存垃圾"。
   实测 `BattlePlayerBase` 有 106~443 个同类实例可做统计。

5. **DTO 交叉（免费真值，最实用）**
   服务端 DTO 已经携带同一语义：
   * `S_COMBAT_OPPONENT.uid/hero_id/life/grade` ↔ 对方 `BattlePlayerBase`
     `+0x10/+0x18/+0x1C/+0x24` —— 真机已验证完全一致；
   * `S_TAVERN_PLAYER_INFO.uid/cur_grade/life` ↔ 每个玩家；
   * `S_COMBAT_SETTLEMENT.damage` ↔ 血量差。
   于是"反解布局"可以完全自动化：**用 DTO 的值当已知值**，不需要人工输入。

6. **事件差分（自动产生新真值）**
   在"出牌/受伤/战斗"前后各抓一次对象快照，diff 出变化的字节：
   * 出牌：`HandCards.Count` 和 `HandCardNum` 同时 -1；
   * 战斗结算：`Life` 变化量 == `S_COMBAT_SETTLEMENT.damage`；
   * 升级：`Grade` +1、`MaxEvolvePoint` 变化。
   这些差值就是新的"已知值"，且**只依赖游戏事件，不依赖人工读数**。

### 3.3 具体落地：用 DTO 自动给 `BattlePlayerBase` 供真值

```python
# 1) 从活 WorldData 找到双方玩家
```

## 4. 限制 3：系统性地找出"对方场上随从"

### 4.1 L0：最快路径（已知容器；类地址缓存后 1 秒级）

> 注意：`find_class()` 本身要做"字节串扫描 + qword 扫描"两遍全内存，
> 4 个类就要 8 遍。**建议按 pid 缓存类地址**（类地址在一次进程内不变），
> 缓存后 L0 只剩几次指针跟踪，毫秒级。下面的偏移都是真机验证过的。

真机验证过的路径：

```
WorldData (活实例)
  +0x128  CacheBattleResult         : S_COMBAT_OPPONENT
            +0x40  minions          : Il2CppArray<CARD_MINIONS>   <-- 对方场
            +0x50  self_minions     : Il2CppArray<CARD_MINIONS>   <-- 我方场
  +0x130  CacheTavernBattleMinions  : S_TAVERN_BATTLE_MINIONS
            +0x18  cards            : Il2CppArray<CARD_MINIONS>   <-- 我方场（实测 7 张）
  +0x198  Opponent                  : Sv2WarchessBattlePlayerBase
            +0x10 uid / +0x18 hero / +0x1c life / +0x24 grade
            +0x60 BattleCards       : List<Sv2WarchessBattleCardBase>
```

`CARD_MINIONS`（`Netease.GameNet.MOS_PROTO`，基类 `ProtoBase`）：

```
+0x18 unit_id (int)   +0x1c card_id (int)   +0x20 atk (long)   +0x28 life (long)
+0x30 evolve_state (short)   +0x32 buff_state (short)
+0x38 skills (CARD_SKILLS[]) +0x40 buff_info (BUFF_INFO[])
+0x48 locked +0x4a left_skill_times +0x4c buy_list_index
+0x50 stack_num +0x54 green_effect +0x58 damage_after_stop +0x5a star (short)
+0x68 atk_count  +0x78 has_select_skill
```

**容器读取代码**（这是旧工具最关键的修复）：

```python
def read_array_refs(mem, arr, maxn=12):
    """Il2CppArray<T>，T 为引用类型。
       对象头 0x10，bounds@+0x10（SZARRAY 为 0），max_length@+0x18，
       元素指针从 +0x20 开始，每 8 字节。"""
    head = mem.read(arr, 0x20)
    bounds = u64(head, 0x10)
    n      = i64(head, 0x18)
    if not (0 <= n <= maxn) or bounds != 0:
        return None
    return [u64(mem.read(arr + 0x20 + 8*i, 8)) for i in range(n)]
```

对比旧 `read_list_objects()`（错在把 Array 当 List）：

```python
items = u64(head, 0x10)   # ← 实际是 bounds（0），不是 _items
size  = i32(head, 0x18)   # ← 实际是 max_length
```

### 4.2 L1：容器无关的搜索（不预设任何类/字段）

这是对"不依赖某个类的列表字段"的正面回答。三步，全部 O(内存)，不猜。

#### 第 1 步：卡 ID 值扫描（1 遍全内存）

```python
ids = {所有 baseCardId ∪ cardIds}          # 174 个（87 张 × 变体）
for chunk in regions(private_only=True):    # 8MB 分块
    a = np.frombuffer(chunk, dtype='<u4')
    idx = np.searchsorted(sorted_ids, a); clip
    hit = sorted_ids[idx] == a
    → 记录 (addr, id)
```

实测：**5,336 命中 / 20.8 秒**。
理论误报：随机 4 字节整数命中 174 个 ID 的概率 ≈ 174 / 2³² ≈ 4×10⁻⁸；
5.4GB ≈ 1.35×10⁹ 个 int 槽 → 约 55 个随机命中。所以**必须**用后面的
"按类聚合 + 支持度 ≥2"过滤。

#### 第 2 步：记录模板反推（不假设类名）

对每个命中 `(addr, id)`，尝试 `base = addr - off`，`off` 从 `0x10` 到 `0x300`
（4 字节步进，要求 `base % 8 == 0`）：

```
klass = qword(base)          # 对象头
name  = klass_fullname(klass)  # Il2CppClass: name@+0x10, namespace@+0x18
vote[(klass, off)] += 1
```

然后**每个类只保留支持度最高的那个偏移**——一个类的 `card_id` 字段只可能在
一个偏移上；这一步同时干掉了"对象等距排列"造成的别名（`true + stride*k`）。

实测反推出 **159 种模板**（很多是卡牌主数据表，如
`WarchessSkillMaster@0x18`、`BuffInfo@0x10`、`CardMaster@0x14`、
`Sv2WarchessCardParameter@0x10`；真正的随从记录是
`CARD_MINIONS@0x1c`、`MINION_BRIEF@0x1c`、`BuildInfo@0x10`）。

> 为什么必须用"值 ∈ 卡表"而不是"8 位数"：
> 旧工具把 `800000xx` 当卡 ID，那是**指针低 32 位**。
> 例如 `0x7FF804C4B3F2` 的低半字是 80,000,000 左右，
> 8 位数、但不在 174 个卡 ID 里 → 卡表命中 0%。
> **判据必须是集合成员，不是数值范围。**

#### 第 3 步：容器与 owner 反推（2 遍全内存）

```
1) 反向指针：一遍 qword 扫描，找出所有指向"记录地址"的位置 site
   实测：3,725 条记录 → 9,092 个指针，46.0 秒

2) 数组判定：对每个 site，尝试 k = 0..11：
       arr = site - 0x20 - 8*k
       bounds = qword(arr+0x10) == 0
       n      = qword(arr+0x18) ∈ [k+1, 12]
       每个元素 p = qword(arr+0x20+8*j) 的 card_id(p+0x1c) ∈ 卡表
   → 这就是一个 Il2CppArray<记录类型>

3) owner 反推：再一遍 qword 扫描，找出指向该数组的字段 site2
   对 site2 向前试 0x10..0x600 的字段偏移，找 klass 头；
   优先用元数据验证"该类在 +off 处确实声明了 记录类型[] 字段"。
   实测 owner 被正确认领：
       S_COMBAT_OPPONENT +0x40 (minions)
       S_COMBAT_OPPONENT +0x50 (self_minions)
       CARD_MINIONS +0x40 (buff_info)      ← 元数据 join 连"buff 数组"也认对了
```

复杂度：1 遍 int + 2 遍 qword。本机对当前进程（私有内存）实测 **20.8s（int）+
46.0s（第二遍指针）+ 数组/owner 开销 = 61.3s**；按 5.4GB 线性外推约 **2 分钟**。
一次扫描后缓存地址，后续读 O(1)。

#### 打分（把"随从数组"从"卡牌主数据/buff 数组"里挑出来）

```
score = 10 * 卡表命中率
      + 2  * (1 <= 数量 <= 7)
      + 2  * star 命中率          # minion 记录才有 star 字段
      + 5  * (owner 字段经元数据验证)
```

实测排行（节选）：

```
[0] score=19.0 record=CARD_MINIONS n=7 hit=100% star=100%
    owner=S_COMBAT_OPPONENT +0x50      ← 我方场 self_minions
[1] score=19.0 record=CARD_MINIONS n=7 hit=100% star=100%
    owner=S_COMBAT_OPPONENT +0x40      ← 对方场 minions ✓
[2] score=19.0 record=CARD_MINIONS n=7 hit=100% star=100%
    owner=S_COMBAT_OPPONENT +0x40      ← 上一场的 DTO（历史实例）
[3] score=17.0 record=BUFF_INFO   n=2 hit=100% star=0%
    owner=CARD_MINIONS +0x40           ← buff 数组，被 star 过滤掉
```

注意 [2]：内存里同时存在多个历史 `S_COMBAT_OPPONENT` 实例。
**必须用"活根"筛选当前那一个**：`WorldData+0x128` 指向谁，或
DTO.uid == 当前 `Opponent` 的 uid。L1 只负责"发现"，L0 负责"定位当前"。

### 4.4 验证方法（不要"看起来像"）

必须同时满足：

1. **卡 ID 命中**：`card_id ∈ 174 个 ID`，要求 **100%**（不是 80%）。
2. **星级匹配**：`star` 与 `cards.json` 的 `star` **100%** 相等。
   这是独立于 ID 的第二维；随机记录同时满足两者的概率趋近 0。
3. **owner 元数据验证**：`owner` 类在 `+off` 处声明的字段类型确实是
   `CARD_MINIONS[]`（或对应记录类型的数组）。
4. **uid 交叉**：`DTO.uid == Opponent.BattlePlayerBase.UserId == WorldData.OpponentUid(+0x118)`。
   真机已满足。
5. **与己方 disjoint**：对方 7 张与 `self_minions` 7 张的 `(card_id, uuid)`
   集合不重叠（允许同卡不同 uuid）。
6. **数量 1..7**（场上上限 7）。
7. **反证**：把偏移人为 ±8，必须得到 0% 命中；把 DTO 的 `minions` 指针换成
   `self_minions`，读出的集合必须等于我方场。
8. **独立来源**：UI 视图 `BattleView._oppoPlayer._fieldCards` 的 `BaseCardId`
   （相对偏移 `FieldCardViewBase+0x64`，`Star = BaseCardId + 0xC`）应与 DTO 一致；
   或者用截图 OCR 做人眼复核（项目已有截图工具）。

### 4.5 如果今后走不通，如何判定"不行"

先跑 §4.4 的 1~3。如果在一个"对方明牌显示 7 张"的对局里：

* 全内存 `card_id` 命中集合里，**没有任何一个数组/列表**的成员数在 1..7
  且 100% 命中卡表；
* 或者所有候选的 owner 都不是"活对象"（不可从 WorldData/BattleView 到达）；
* 或者候选集合与屏幕 OCR 不一致；

那么结论是：**该版本客户端没有收到对方卡 ID**（服务端裁剪/加密），
只读内存无解。此时不要再扫内存，改走 OCR/图像识别。
本版本**不是**这种情况（§1.4 已 7/7 命中）。

## 6. 局限与风险

1. **版本变化**：HybridCLR 热更新会替换 `.bytes`。偏移可能变，但
   `研究-exact_layout.py` 每次从磁盘元数据重算，不依赖硬编码；
   `研究-find_opponent.py` 的 L1 也不依赖偏移。所以**版本更新后先重跑 verify**。
2. **元数据只覆盖热更新程序集**：AOT 类型（UnityEngine、System）只能靠
   外部结构体表；遇到新的 AOT 值类型，布局可能整体偏移——用 `verify`
   或把该类型的实例值喂给 `研究-layout_csp.py` 发现。
3. **陈旧对象/对象池**：`WorldData` 443 个、`S_COMBAT_OPPONENT` 98 个、
   `BattleCardBase` 336 个——按 klass 扫实例必须做"活根"验证，
   否则会读到上一局甚至几天前的数据。
4. **GC**：IL2CPP 用 Boehm（非移动），地址在一次进程内稳定；
   但对象会被复用，字段可能残留旧值。
5. **只读**：所有代码只用 `OpenProcess(PROCESS_VM_READ)` + `ReadProcessMemory`，
   不写内存、不注入、不 hook。扫描大内存时注意游戏可能掉帧（建议只扫
   `MEM_PRIVATE`）。
6. **卡表覆盖**：`cards.json` 只有 87 张（含 token），若出现表外卡（新模式），
   卡 ID 判据会失效；届时需要扩充卡表或退回"结构 + OCR"双重验证。

## 8. 一句话总结

* **限制 1/2**：布局不应该"反解"——元数据能算死；真要反解时，
  用"硬约束 + 引用 oracle + 多实例 + 逐字段可行性检验"，
  算法会**证明唯一**或**告诉你缺哪个见证**，绝不瞎挑。
* **限制 3**：对方场在 `S_COMBAT_OPPONENT.minions`（`Il2CppArray<CARD_MINIONS>`，
  `card_id@+0x1c`），根因是"基类 +8"和"Array 当 List"；
  通用发现算法是"卡 ID 值扫描 → 记录模板 → 容器/owner"，
  61 秒一次、100% 卡表命中即可判定为真。
