日期：2026-10-17 18:0x　目标进程：`D:\Shadowverse\MuMu模拟器x影之诗高清版.exe`
所有结论均为**只读**操作得出：`OpenProcess(PROCESS_VM_READ)` + `ReadProcessMemory`，

**技术上成立，且三条主干链路已实测打通两条半**：进程读取权限无阻（6,055.9 MB 堆 18.2 秒扫完）、

## 1. 静态分析成果（本次最大产出）

### 1.1 分水岭发现：这些类型不在 IL2CPP 里

在三个文件里逐个搜索关键符号（mmap + 二进制搜索）：

| 符号 | global-metadata.dat (41.1 MB) | GameAssembly.dll (174.4 MB) | sv2Warchess.bytes (2.09 MB) |
|---|---|---|---|
| `CombatOpponent` | ✗ | ✗ | **✓ @0x17F05F** |
| `OpponentMinions` | ✗ | ✗ | **✓ @0x17EB4B** |
| `S_COMBAT_OPPONENT` | ✗ | ✗ | **✓ @0x172858** |
| `isRoundLevel` | ✗ | ✗ | **✓ @0x1929D0** |
| `opponent_user_info` | ✓ @0x3EAB69（是 AOT 侧标识符） | ✗ | ✓ @0x19A3B7 |

**含义（重要，决定了整个技术路线）**：
`Netease.GameNet.MOS_PROTO.*` 这些对局 DTO 是 **HybridCLR 热更新程序集里的解释器类型**，
不是原生 IL2CPP 类型。所以：

- **Il2CppDumper 那一套"全局偏移表"对它们完全无效** —— 因为它们的 Il2CppClass 是运行时由
  HybridCLR 动态注册的，不在 GameAssembly 的静态 `Il2CppMetadataRegistration` 里。
- 必须走"运行时发现"：先定位类名字符串 → 找指向它的 `Il2CppClass*` → 再找实例。
  这条路我已跑通（§2）。

### 1.5 字段偏移：三种假设并存，靠数据自动判定

字段偏移不在元数据里，只能推。三个候选：

**(a) 声明顺序 + 自然对齐（我倾向上认为是对的）**

```
uid 0x10 | hero_id 0x18 | life 0x20 | armor 0x28 | grade 0x30 | random_num 0x34
minions 0x38 | evolve_point 0x40 | cards_num 0x44 | self_minions 0x48 | self_cards 0x50
skills 0x58 | skill_cost 0x60 | … | can_use_hero_skill 0x86   总长 0x88 = 136
```

**(b) 按宽度降序（CoreCLR AutoLayout 风格）**：`grade` 会被挤到 **0x74**，`life` 到 0x18。
总长同为 0x88。

**(c) 8 字节槽位（你给的假设）**：每个字段占一个槽，总长 25×8+0x10 = **0xD8 = 216**。

我**没有实测证据**判定哪一种是真（原因见 §2.6）。所以脚本不押注，**三种都算一遍**，用合理性打分
（uid 9~12 位、hero_id 1~10000、life -20~120、grade 1~12、minions 是 8 字节对齐的堆指针 ……）
挑最高分的组合，并把命中的布局名打印出来。

> 对 `CARD_MINIONS` 更狠：`card_id` 的偏移不靠推，直接**暴力扫 0x10~0xA0 每 4 字节**，
> 用"这个值能不能在 `cards.json` 里查到"当打分函数，命中率最高的那个偏移就是真偏移，
> 并据此对整个布局做等距校正（`delta`）。这条在真机上一跑就能自证，不需要人肉对齐。

## 3. 风险清单（逐条，按"能不能被看见"分类）

先说结论：**打开一个只读句柄这件事，在当前静态证据下没有发现会被检测的机制；
但"没有证据"≠"证明没有"，我列出我实际看到的证据。**

### 3.1 反作弊/风控组件静态体检（读 DLL 字符串，零风险）

| 组件 | 大小 | 命中特征 | 判读 |
|---|---|---|---|
| `CrashHunter_PC3.dll` | 3.4 MB | `OpenProcess`+`GetCurrentProcessId`、`CreateToolhelp32Snapshot`+`Module32First`、`IsDebuggerPresent`、**`DetourTransactionBegin` / `DetourUpdateThread`**、`DebugActiveProcess` 未命中、**`ReadProcessMemory` 未命中** | 崩溃捕获 + **微软 Detours 内联 hook 引擎**（用于 hook 自己的崩溃处理），具备进程/模块枚举能力，但**没有跨进程读内存的字符串** |
| `CrashHunterMisc.dll` | 366 KB | `IsDebuggerPresent`、`CreateRemoteThread` | 同上，崩溃上下文采集 |
| `OrbitSDK.dll` | 8.0 MB | `OpenProcess`、`CreateToolhelp32Snapshot`、`Module32`、`IsDebuggerPresent`；`anti` 命中是 **`anti_replay`（OpenSSL/DTLS）误报** | 数据统计 SDK，无 anti-cheat 语义 |
| `NtUniSdkBase/RoostX` | 6–11 MB | `CreateToolhelp32Snapshot`、`Module32`、`anti`（同样是 OpenSSL 误报） | 登录/支付/渠道桥接 |
| `EnvSDKLib.dll` | 6.5 MB | `WriteProcessMemory`、`CreateToolhelp32Snapshot` | 环境采集；导入表里有 `WriteProcessMemory` 不代表会对你用 |

安装目录里**没有任何 `.sys` 驱动**，也没有内核回调（`ObRegisterCallbacks`）的迹象。
`CrashHunter` 的实际行为是"hook 自己进程里的函数、抓崩溃栈、`OpenProcess(GetCurrentProcessId)` 读自己的内存"，
这是标准崩溃上报形态，不是内核反作弊形态。

### 3.2 逐操作风险表

| 操作 | 在游戏进程内读写内存？ | 可见性 | 判读 |
|---|---|---|---|
| B 方案（只读本地文件/日志） | 否 | 完全不可见 | **零风险**（本次已做，见 §5.1） |
| `OpenProcess(PROCESS_VM_READ)` 开句柄 | 是（只读） | 必须由**外部进程**发起；游戏侧若无驱动/句柄回调则看不见 | **低**。我已实测成功，且 `ReadProcessMemory` 也不失败 |
| 全量扫 6 GB | 是（只读） | 同上；会短时吃 CPU/IO | **低**（页错误会让游戏略微卡顿 0.2~1s） |
| 写内存 / hook / 注入 DLL | 是（写） | `Detour*`/`Module32First` 这类能力足以发现"模块列表里多了个东西" | **高，不建议** |
| 自动化输入（模拟点击/自动打牌） | 否，但产生异常输入序列 | **服务端行为分析一定能看出来** | **高，且这是真正会封号的一类** |
| 只"看"不"动"（本方案） | 是（只读） | 客户端本地不可见；服务端看不到任何额外请求 | **中低** |

### 3.3 与用户初衷的冲突（必须点明）

用户原本的立场是"**为了防外挂核查，要和游戏独立，只靠截图**"。
这条路线**直接违背**它：它要求进程正在运行、要求读它的私有内存、且脚本一旦失手（比如以后为了
"自动刷新"而写内存/hook），风险等级会从"低"跳到"高"。

我的建议写在 §6。**如果用户只是"想知道对方等级"，最省事且零风险的是 §5.1 的
"点头像 + 缓存实验"，其次才是这个脚本。**

### 4.1 原型用法

**一条命令，复制粘贴即可（不需要任何参数）：**

```powershell
& "C:\Users\33949\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe" "C:\Users\33949\Documents\deepseek-harness\default-workspace\svwb-probe\shadow_warchess_reader.py"
```

它会做什么：按 `BattlePlayerBase → TavernOwnerData → S_TAVERN_PLAYER_INFO → S_COMBAT_SETTLEMENT → S_COMBAT_OPPONENT`
的顺序各试一遍，每个源都打印「类找到没 / 引用数 / 实例地址 / 字段值 / 是否通过校验」，同时把每个候选实例
`0x10~0x200` 的原始内存写进同目录的 `dump_<时间戳>.txt`（用记事本直接打开）。

```powershell
# 变体
& $py "$w\shadow_warchess_reader.py" --watch 2     # 每 2 秒刷新，适合边打边看
& $py "$w\shadow_warchess_reader.py" --probe       # 只报"各源命中数"，用来掐时机
& $py "$w\shadow_warchess_reader.py" --json        # 机器可读
```

输出形态（示意）：

```
[BattlePlayerBase ] Sv2Warchess.Sv2WarchessBattlePlayerBase
    类=0x...  引用=2  best_score=11  ✅ 有可信实例(字段校验通过)
      ✔ 0x... layout=decl  uid=1203xxx hero=1070 grade=4 life=28 armor=0
[TavernOwner      ] Sv2Warchess.TavernOwnerData
    类=0x...  引用=1  best_score=6   ✅ 有可信实例(字段校验通过)
      ✔ 0x... layout=decl  grade=5 gold=7 maxgold=10
[CombatOpponent   ] Netease.GameNet.MOS_PROTO.S_COMBAT_OPPONENT
    类=0x...  引用=90 best_score=12  ✅ 有可信实例(字段校验通过)
  ✔ 0x... layout=decl  uid=... hero=1070 grade=4 life=35 armor=0 cards=6
  对方场上 (3):
    10501110  挥舞的怪物   2★  6/7
  我方场上 (2):

```

**"✅ 有可信实例 / ⚠ 无可信实例" 怎么读**：✅ 表示 `uid + 英雄 + 血量 + 等级` 四个值同时落在合理区间
（等级 1~8、血量 0~100、英雄 1~10000、uid 是 12 位左右的数字）。这是硬校验，**宁可报"没有"也不把
垃圾值当成对方等级**。⚠ 通常只意味着"现在不在战斗阶段"，不是脚本坏了。

### 4.2 一次运行能拿到什么 / 失败时怎么看诊断

- **成功**：每个源一行摘要，`✔` 标出的实例就是可信的；`grade` 是幻境等级（我方看 `TavernOwner`，
  对方看 `CombatOpponent` 或 `BattlePlayerBase` 里两个实例中不是自己的那个）。
- **失败**（全是 ⚠ 或"类未找到"）：说明**当前不在对局/不在战斗阶段**——这不是故障，是数据还不存在。
  先开一局，或先用 `--probe` 看 `BattlePlayerBase` 什么时候从 0 变成 2，那一刻再跑正式命令。
- **想知道脚本猜的字段位置对不对**：打开 `dump_<时间戳>.txt`。里面是每个候选实例从 `+0x10` 起每 8 字节一行，
  四种解释（qword / int64 / int32 / int16）并排，`ptr?` 列标注"看起来像堆指针"。人眼扫一眼就能看出
  真实布局，不需要懂代码。

### 4.3 日志路线的最终确认（走不通）

`Player.log` 里 `damage` 出现 **0 次**、`COMBAT` 出现 **0 次**，`SETTLEMENT` 的 3 次全部只是
`SettlementFinishBlowAction` 的**方法名栈帧**，不含任何 JSON 内容。日志只记录"调用了哪个方法"，
不记录参数值 → **`S_COMBAT_SETTLEMENT.damage` 只能从内存拿，日志里没有**。

### 4.4 首次运行要确认的三件事（判定表）

| 现象 | 含义 | 处理 |
|---|---|---|
| `layout=decl` 且 ✔ | 声明顺序布局成立（我的主假设） | 把三布局砍成一个，速度×3 |
| `layout=slots` / `layout=width` 才 ✔ | HybridCLR 用的是槽位/宽度排序布局 | 保留该布局，删其余 |
| 全是 ⚠ 但确实在对局中 | `S_COMBAT_OPPONENT` 已 GC 或仍不在战斗阶段 | 改看 `BattlePlayerBase`（战斗中恒有 2 个实例）；或用 `--probe` 掐时机 |
| 全是"类未找到" | 不在对局 / 类名被改 | `--probe` 看是否 0；若对局中仍 0，需重新出 `_types_warchess.txt` |

## 5. 补充（降级但仍完成的 A/B）

### 5.1 B 方案实测结论（零风险）

| 位置 | 发现 | 判断 |
|---|---|---|
| `Persistent\d\SaveData.db`（36 KB, 257 行） | `AppSetting(save_key BLOB, save_value BLOB)` | **键和值全部加密**（每条 key 都是高熵二进制，value 4~603 字节），**无明文**。是网易本地存档加密（类 XXTEA），不值得破 |
| `Persistent\d\FieldGimmickStatus.db` 等 6 个库 | 表结构同上，行数 0~5 | 只存设置，不含对局状态 |
| `Persistent\meta`（23.3 MB SQLite） | 表名被混淆成 `a / ln / le / r / c / i`，共 7 表 | **纯静态主数据**，与实时对局无关 |
| `Persistent\dat\XX\<26位大写字母数字>` | about 1500 个文件，5 KB~700 KB | 按哈希命名的下载缓存（asset bundle），非状态 |
| `Player.log`（790 KB，实时） | **有网络回调的完整调用栈**：`BattleProxy:TavernFrozenStatCallBack(S_TAVERN_FROZEN_STAT) → NetMsgBroadcastInfo\`1:Parse(String) → NetMsgBroadcast:BroadcastMsg(UInt32, String) → GameNetWork:OnProccessNetMessage()` | **只暴露"调了哪个回调"，不含消息体数值**。能证明 `BroadcastMsg(uint, String)` 内部是**明文字符串 JSON**（加密在更下层 transport），但对拿数值没用 |
| `%LOCALAPPDATA%\netease\UniSDK\Drpf\ma68-64-mcount_drpf.db` | 28 KB 统计库 | 埋点计数，无对局数据 |

**结论：客户端本地不落地对局状态。** 状态只存在于内存 + 加密流量。这也从反面解释了为什么
"截图看不到对方等级"就必须读内存或解密流量 —— 没有第三条本地文件的路。

### 5.2 A 方案（缓存实验，零风险，建议先做）

目的：判断"点头像看等级"是**本地已有数据**还是**现拉服务端**。这决定了不用内存也有没有别的机会。

1. 进对局，**战斗阶段**，点对方头像 → 记下等级（如 4），**立刻关掉**。
2. 用手机秒表/录屏计时，等 **10 秒**（让任何缓存/请求状态稳定）。
3. 断网（拔网线/关 WiFi）或开飞行模式，**再点一次**对方头像。
4. 观察三种结果：

| 现象 | 判定 | 后续含义 |
|---|---|---|
| **断网后仍立刻显示 4** | 值在**客户端内存/本地缓存** | 与 §2 的内存路线互相印证；也说明"离线可见" |
| 断网后转圈/报错/显示占位 | **每次点都发请求** | 说明 UI 是"按需拉取"，`S_COMBAT_OPPONENT` 里可能并没有 `grade`（要复核 `grade` 是否只是段位） |
| 断网后显示的是**上一次**的值（对方已升级却显示旧值） | 有缓存但会失效 | 缓存位置可进一步找（但已加密，价值有限） |

5. 恢复网络，让对方升一级，再点头像：**值是否变化** —— 变了说明是实时拉，不变说明缓存了战斗开始时的快照。

这个实验 3 分钟做完，能直接回答"`grade` 是不是战斗开始时就已经在客户端了"。若答案是"是"，
内存路线就是**唯一且合理**的读法（因为本地文件已加密，见 5.1）。

## 6. 建议：这条路值不值得长期维护

**值得，但只值得当"只读仪表盘"，不值得当"自动化工具"。**

优点（意外地好）：

- **抗版本更新**：不依赖任何硬编码偏移或 RVA。类名 `S_COMBAT_OPPONENT` / 字段名来自加密程度很低的
  元数据，只要网易不改字段名，脚本跨版本可用；改了我 30 秒就能从 `_types_warchess.txt` 里重新生成。
- **只读、无 hook、无注入**：这是它能被接受的前提，也是最容易被越界破坏的前提。
- 顺带拿到了 `S_COMBAT_SETTLEMENT.damage`：**扣血公式可以直接验证而不必反推**，
  这比 E 方案的整数规划可靠得多。

代价与红线：

1. **必须游戏在跑、必须读它的私有内存**，与"与游戏独立"的初衷相反。若用户很在意这个立场，
   应该退回到 A（缓存实验）+ 截图，接受"点一次头像"这个动作。
2. **绝对不要**为了"自动刷新/自动操作"去写内存、hook 或模拟输入 —— 那会把风险从"低"直接推到"高"，
   而且服务端行为分析对异常输入序列的识别是成熟能力。
3. 每次版本更新后**跑一次 `probe_scan.py` 确认类名还在**，再跑 reader。这是唯一的维护动作。

**对"要不要删掉扣血计算"的回答**：不用删，但要改定位。
扣血公式 `伤害 = 胜方等级 + 胜方残存随从星级和` 现在可以直接用 `S_COMBAT_SETTLEMENT.damage` 校验；
建议保留公式作为"预期值"，把服务端下发的 `damage` 作为"真值"，两者不一致时打印出来 ——
这既验证了公式，又不会因为公式记错而给出错误建议。若最终只做截图方案，则公式仍是必需的，
但应标注"等级来自用户手动点开确认"，把不确定性显式化。
